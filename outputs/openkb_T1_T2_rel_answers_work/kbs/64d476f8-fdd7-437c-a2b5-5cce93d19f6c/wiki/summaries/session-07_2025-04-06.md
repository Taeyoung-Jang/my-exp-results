# Summary of Session 7 (2025‑04‑06)

## Overview
This conversation provides a hands‑on, low‑friction approach to **compliance and audit readiness** by embedding evidence collection into existing workflows. It delivers a **checklist of must‑have log sources**, an **[[concepts/audit-bundle]]**, a **one‑page hand‑off** for a typical AWS + GitHub + Jira + Okta + Splunk environment, and refined **Splunk SPL** queries that normalize multivalue fields and accommodate custom Jira approval fields.

## Key Concepts
- [[concepts/compliance-automation]] – Using existing tools to capture evidence automatically.  
- **Log source checklist** – Core log and artifact categories required for a quarterly audit (plain text).  
- [[concepts/audit-bundle]] – Structured export package with naming conventions and time‑range rules.  
- [[concepts/splunk-spl-standardization]] – Precise SPL statements for consistent data extraction.  
- **Multivalue normalization** – `mvexpand`/`mvjoin` patterns to flatten array fields (plain text).  
- **Custom approval fields** – Placeholder approach for Jira issue‑type filtering and custom approval metadata (plain text).

## Must‑Have Log Sources & Evidence Artifacts
| Log Source | Evidence | Automated Collection Point |
|------------|----------|----------------------------|
| Identity & Access (Okta) | Auth events, privilege changes, group membership | Stream to **SIEM** (Splunk) |
| Change Management & Approvals (Jira) | Closed change tickets, linked approvals | Export via SPL from Jira index |
| CI/CD Pipeline Runs (GitHub Actions) | Build history, test results, deployment hashes | Forward to **SIEM** |
| Infrastructure & Application Logs (AWS CloudTrail & CloudWatch) | Service restarts, config changes, errors | Agents / Cloud‑native log services |
| Vulnerability Scan Results | Scan summaries, dependency checks | Push to **SIEM** via API |
| Endpoint Security Telemetry (EDR) | Detection events, patch status | Forward to **SIEM** |
| Backup & Recovery Evidence | Job status, restore tests | Log streaming to **SIEM** |
| SaaS Audit Logs (Third‑party) | Admin actions, configuration snapshots | API integrations to **SIEM** |
| Policy Acknowledgments & Training | Completion records | Export from HRIS / training platform |

## Audit‑Bundle Template (Quarterly)
- **IAM Export** – `Okta_IAM_QX_YYYY.json` (full quarter + 7 day buffer, defined fields).  
- **Change Management** – `Jira_Changes_QX_YYYY.csv` (Done tickets, approvals, links).  
- **CI/CD Deployments** – `CICD_Deploys_QX_YYYY.zip` (pipeline runs, artifact hashes).  
- **Infra & App Logs** – `InfraApp_Logs_QX_YYYY.zip` (high‑value streams only).  
- **Security Controls** – `Security_Controls_QX_YYYY.zip` (vuln scans, EDR, backup reports).

## One‑Page Hand‑off for AWS + GitHub + Jira + Okta + Splunk
1. **Okta** – Export System Log with SPL (see below). Save as `Okta_IAM_QX_YYYY.json`.  
2. **Jira** – Run JQL for change projects, status = Done, date range; export selected fields to CSV.  
3. **GitHub PR Merges** – Filter merged PRs by date; export PR metadata and reviewer info.  
4. **GitHub Actions** – Export workflow runs, conclusions, job status.  
5. **AWS CloudTrail** – Filter by target services; export key fields.  
6. **Splunk Security Controls** – Run quarterly searches for vulnerabilities, EDR, backups; bundle as ZIP.

## Revised SPL Queries (Normalization & Custom Fields)

### GitHub PR Merge (multivalue handling)
```spl
index=github earliest=START latest=END action="pull_request" pull_request.merged=true
| eval reviewers=mvjoin(requested_reviewers, ",")
| mvexpand reviews
| eval review_users=mvjoin(reviews.user.login, ",")
| eval review_states=mvjoin(reviews.state, ",")
| table _time repo.name pull_request.number pull_request.title pull_request.user.login \
        pull_request.base.ref pull_request.head.ref pull_request.merged_at \
        pull_request.merge_commit_sha reviewers review_users review_states commit.sha
```
*Uses multivalue normalization to produce a stable table.*

### Jira Change‑Type Issues with Custom Approval Fields
```spl
index=jira earliest=START latest=END issue.type IN ("Change","Normal","Emergency")
| search CUSTOM_APPROVAL_FIELD="*"   # replace with actual field name
| table _time issue.key issue.summary issue.reporter issue.assignee issue.created \
        issue.updated issue.resolutiondate issue.type CUSTOM_APPROVAL_FIELD \
        CUSTOM_APPROVER_FIELD issue.status
```
*`CUSTOM_APPROVAL_FIELD` and `CUSTOM_APPROVER_FIELD` are placeholders for the organization’s specific approval metadata.*

## Common Gap Areas (Top 5)
1. **Missing IAM privilege‑change logs** – not fully streamed to SIEM.  
2. **Incomplete CI/CD artifact hashes** – breaks traceability.  
3. **Ticket‑to‑code link loss** – approvals recorded but not tied to merge SHA.  
4. **Exported infra logs lack immutable packaging** – auditors cannot verify completeness.  
5. **Training & policy evidence lives outside the SIEM stack** – often omitted.

## Takeaways
- Embed evidence capture in the tools teams already use to keep compliance low‑friction.  
- Standardize export **naming**, **time ranges**, and **field lists** to avoid ad‑hoc work each quarter.  
- Leverage **Splunk SPL** with `mvexpand`/`mvjoin` for reliable, repeatable data extracts.  
- Treat custom Jira approval fields as configurable placeholders for easy adaptation.  
- Regularly audit the pipeline itself to ensure the four core data sources (SIEM, ticketing, CI/CD, IAM) remain complete.
