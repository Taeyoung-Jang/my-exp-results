## Overview
This session provides a concise, actionable framework for building a **future‑proof personal archive**. It covers preferred file formats, a minimal yet scalable folder hierarchy, clear naming conventions, metadata handling, backup strategies, and best practices for organizing multi‑year projects.

## Recommended Open Formats [[concepts/open-formats]]
- Text & notes: plain text or [[entities/markdown]]
- Images: [[entities/jpeg]] / [[entities/png]] with EXIF/​XMP
- Video: [[entities/mp4]]
- Audio: standard lossless or compressed formats
- Documents: [[entities/pdfa]] for long‑term readability

## Folder Structure [[concepts/folder-structure]]
```
Archive/
├─ Documents/
├─ Photos/
├─ Video/
├─ Audio/
├─ Projects/
└─ Personal Notes/
```
- Top‑level categories are stable and human‑readable.
- Within each category, organize by **year** (e.g., `Photos/2026/2026‑03‑Trip‑to‑Japan`).
- For projects, use a permanent slug under `Projects/` (e.g., `Projects/project‑aurora/`).

## Naming Conventions
- Chronological files: `YYYY‑MM‑DD‑keyword‑description.ext`
- Non‑date‑specific files: clear, descriptive names (e.g., `README.md`, `specifications.pdf`).
- This pattern sorts naturally and conveys context without opening the file.

## Metadata Strategy
- **Embed** whenever possible: EXIF/​XMP for images, front‑matter for Markdown files.
- Avoid reliance on external databases.
- Maintain a separate **README** at the project root for cross‑file context that cannot be embedded.

## Backup Strategy [[concepts/backup-strategy]]
- Follow a simplified **3‑2‑1** rule:
  1. Primary archive on the main computer.
  2. Mirrored copy on a local external drive.
  3. Cloud backup with versioning.
- Enable checksums or integrity verification if supported.
- Periodically test restores.

## Multi‑Year Project Organization
- **Option A** (recommended): `Projects/project‑slug/` with year subfolders (e.g., `2024‑notes`, `2025‑drafts`).
- Keeps the project as a single, stable container, avoiding link rot and duplication.
- Non‑time‑bound assets (README, final outputs, scripts) reside in the project root.

## Project README Design
- Serve as a front door, not a diary.
- Sections:
  1. **Project Overview** – one‑paragraph description.
  2. **Structure Summary** – list of root items and year‑folder purpose.
  3. **Getting Started** – where to begin after a hiatus.
  4. **Milestones** – high‑level timeline (major releases, key events).
  5. **Further Documentation** – links to detailed logs or separate files.
- Keep the README concise; move detailed logs to their own files.

## Preference for Project Organization (A vs B)
- **Option A** (single project home with internal year folders) is more resilient over 20 years.
- It eliminates external linking, reduces the risk of broken references, and keeps all project context together.
